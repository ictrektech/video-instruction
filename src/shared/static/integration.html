Video Instruction · 接入文档

视频场景检测（scene-detect）与视频结构化（structure）双服务 HTTP API，供 VOS 平台内其他应用调用。

开始 服务概览 访问地址 接入流程 接口 scene-detect structure describe 响应结构与错误码 契约 video_path 规则（推荐 URL） 任务生命周期 产物与释放 服务端配置 接入检查清单

服务概览

两个独立部署的 FastAPI 服务，各自内嵌 Huey worker，互不依赖；structure 可引用 scene-detect 的 job 结果。

服务容器端口宿主端口职责
scene-detect891048910 ffprobe 取元数据 → PySceneDetect 检测场景边界 → 返回 scenes[]
structure891148911 按场景抽帧拼九宫格 → 写 staging → 打包 tar；可选 VLM 场景描述
服务是无状态的：不持有视频资产，产物由调用方主动下载（Pull），下载后显式释放。
视频由调用方以 http(s):// URL 提供（推荐），服务端只按 URL 流式读取， 不依赖共享卷与路径一致性，跨容器/跨主机均可直接处理。详见 video_path 规则。

访问地址

部署形态Base URL
VOS 平台 · 同机直连（推荐） http://172.17.0.1:48910 / http://172.17.0.1:48911
VOS 平台 · 经 Traefik 网关 http://${VOS_HOST_GW_IP}:${VOS_API_GW_PORT_INTERNAL}/api/com.ictrek.video-structure/{detect|structure}
独立 Docker Compose http://<host>:${SCENE_DETECTION_PORT:-8910} / ${STRUCTURE_PORT:-8911}

健康检查：GET /api/health（两服务均有）。响应： {"code":0,"msg":"操作成功","data":{"status":"ok","service":"scene-detection"}}， structure 服务的 service 为 "structure"。

VOS 内调用方请把 base url 声明在自己的 configs.yml 里（string 类型 + 默认值）。平台不会因为声明了依赖就注入对方地址。

三步接入

1. 提交场景检测（video_path 传视频 URL）

curl -X POST http://172.17.0.1:48910/api/v2/scenes/detect/jobs \
  -H 'Content-Type: application/json' \
  -d '{"video_path": "http://172.17.0.1:38085/api/media/123/stream"}'

2. 轮询结果，拿 scenes

curl http://172.17.0.1:48910/api/v2/scenes/detect/jobs/{job_id}
# data.status = succeeded 时，data.result.scenes 即场景边界

3. 提交结构化（video_path 与第 1 步保持一致）

curl -X POST http://172.17.0.1:48911/api/v2/video/structure/jobs \
  -H 'Content-Type: application/json' \
  -d '{"video_path": "http://172.17.0.1:38085/api/media/123/stream", "detect_job_id": "{job_id}"}'
# -> data.job_id 即下面的 {structure_job_id}

4. 轮询 structure 状态（关键，别跳过）

curl http://172.17.0.1:48911/api/v2/video/structure/jobs/{structure_job_id}
# 等到 data.status == "succeeded"，且 data.artifact.describe_status != "pending"

5. 下载产物 + 释放

curl -o structure-{structure_job_id}.tar \
  http://172.17.0.1:48911/api/v2/video/structure/jobs/{structure_job_id}/artifact
curl -X DELETE http://172.17.0.1:48911/api/v2/video/structure/jobs/{structure_job_id}
/artifact 不是轮询接口：它只在任务成功后一次性返回 tar，未就绪直接 409。 轮询请打 GET /structure/jobs/{id}；若启用了 describe，还要等 describe_status 从 pending 离开，否则 artifact 仍返回 409。
也可以跳过第 1、2 步，直接把已有的 scenes 数组传给第 3 步（字段 scenes 与 detect_job_id 二选一）。

GET /api/v2/video/structure/jobs/{job_id}/artifact

返回 application/x-tar 二进制流（不是 JSON），响应头 X-Artifact-Describe-Status: none|succeeded|failed。

调用前必须先轮询状态接口到 succeeded；未就绪直接返回错误（任务未成功 / describe 进行中产物未冻结），该接口本身不支持轮询等待。

状态码含义
200tar 流，Content-Type: application/x-tar
404job 不存在，或 job 类型不是 structure
409任务未成功，或 describe 进行中产物尚未冻结（继续轮询）
410staging 已不存在 / 已释放

错误时返回 JSON：

HTTP/1.1 409 Conflict
Content-Type: application/json

{
  "code": 10002,
  "msg": "不支持的操作: describe 进行中，产物尚未冻结",
  "data": null
}

Job 状态与 job 级错误

data.status：queued → running → succeeded / failed。

data.error 结构：{code, message, detail}，code 取值：

job typeerror.code
scene_detectSCENE_DETECT_ERROR
structureSTRUCTURE_ERROR
describeDESCRIBE_ERROR
created_at / started_at / finished_at 均为 Unix 秒（int），未发生时为 null。 轮询间隔建议 2–5 秒。

video_path 规则（推荐 URL）

video_path 支持三种写法，强烈推荐 http(s):// URL：

形式处理评价
http:// / https:// 原样透传给 ffmpeg/ffprobe 流式读取（自动附加 -rw_timeout / -reconnect* 重连参数） 推荐。只需网络可达，不依赖共享卷与路径一致性
绝对路径 /xxx 直接使用，需该路径在服务端容器内存在且可读 仅单容器自测；跨容器需两边挂载同一卷且路径完全一致
相对路径 拼到服务端 DATA_BASE_PATH 下 兼容旧模式，不推荐新接入使用
为什么推荐把视频暴露成 URL：scene-detect 与 structure 是两个独立容器， 而且可能都不与调用方同机。传本地路径意味着调用方、scene-detect、structure 三方的挂载点与路径必须完全一致， 任何一方部署形态变化（换卷、换宿主、走网关）都会导致 70101 视频文件未找到。 把视频暴露成一个 http(s) 地址后，本服务只需要网络可达即可读取， 与目录挂载彻底解耦，跨容器、跨主机、跨网关都能直接工作。

URL 形态的要求

  • 从服务端容器发起访问：URL 必须能在 scene-detect / structure 容器内访问。VOS 同机部署一般走 172.17.0.1（docker0 网关）访问宿主端口，不要写 localhost/127.0.0.1，那会指向容器自己。
  • 返回真实视频流：Content-Type 为视频类型或直接下载，不要返回 HTML 登录页/跳转页。
  • 建议支持 Range：ffmpeg 会做 seek；不支持 Range 时退化为顺序流，仍可处理但更慢。
  • 有效期要覆盖任务时长：URL 在 queued → running 全程都要有效；带签名 token 的 URL 请把有效期放宽到小时级。
  • token 会被脱敏：URL 中 token= 参数在日志与去重哈希里统一替换为 token=***， 轮换 token 不会导致重复计算，也不会泄漏到日志。

如何把视频暴露成 URL

调用方（如 VOS 媒体服务）自行提供一个可匿名/带 token 访问的视频流端点即可，本服务不限制实现方式。常见做法：

做法示例适用
媒体服务已有的流式接口 http://172.17.0.1:38085/api/media/123/stream 推荐，零改造
对象存储直链 / 预签名 URL https://minio:9000/bucket/a.mp4?X-Amz-Signature=... 已有 OSS/S3/MinIO
静态文件服务 python -m http.server / nginx 把视频目录挂成 HTTP 临时联调
带鉴权时 ...?token=xxx token 自动脱敏，不影响去重 
# 推荐：URL
{"video_path": "http://172.17.0.1:38085/api/media/123/stream"}

# 仅单容器自测：绝对路径（需容器内可见）
{"video_path": "/photos/library/abc.mp4"}

# 旧模式：相对路径（拼到 DATA_BASE_PATH 下）
{"video_path": "library/abc.mp4"}
非 URL 的 video_path 会做本地 is_file() 校验，不存在直接返回 code=70101 视频文件未找到；URL 不做存在性预检，读取失败会体现在 job 的 error.message 里。

URL 对去重的影响

video_path 决定 video_hash，进而决定任务复用：

来源video_hash 算法效果
本地路径内容采样 MD5（3 点 × 16KB）内容相同即复用，但要求服务端能读到文件
http(s) URL脱敏 URL 的 SHA-256URL 相同即复用，不读视频，提交立即返回
因此同一份视频请始终用同一个 URL（不要每次生成不同签名的临时链），否则会被当作不同视频重复计算。

任务生命周期

提交去重相同 video_hash 的未完成任务会被复用
video_hash（本地）内容采样 MD5
video_hash（URL）脱敏 URL 的 SHA-256
队列Huey + SQLite（服务内嵌 worker）
job 保留期7 天（JOB_TTL_DAYS，0=不清理）
staging 保留期STAGING_TTL_SEC：compose 7 天，代码默认 6 小时

产物与释放

structure-{job_id}.tar
├── manifest.json        # 最后写入，产物完整性标志
├── grids/scene_001.jpg  # 每场景一张九宫格
└── descriptions.json    # 可选，describe succeeded 后才纳入

交付模型是 Pull：服务端只暂存，调用方下载后调 DELETE 释放。超时未取由 worker 周期清理。

staging 目录里还有 metadata.json，但它与 manifest.json 冗余，不打包进 tar； 需要元数据请读 manifest.json 的 metadata 字段或状态接口的 result.metadata。

descriptions.json 由 describe 写入，内容对应状态接口 result.descriptions[]。

staging 目录路径存在 job 的 result_ref 里，依赖共享卷。容器内路径为 STAGING_BASE_PATH/<job_id>。

接入检查清单

  • 在调用方 configs.yml 或应用接入内配置，声明两个 base url（scene / structure），默认值填 http://172.17.0.1:48910 与 :48911。
  • 把视频暴露成 http(s):// URL 传入，并确认该 URL 在服务端容器内可访问（VOS 同机经 172.17.0.1，不要写 localhost）。
  • 同一份视频固定使用同一个 URL（不要每次生成新签名），否则去重失效、重复计算。
  • 判断成败只看响应体 code：业务错误也是 HTTP 200。
  • 轮询间隔建议 2–5 秒；/artifact 返回 409 视为"继续等"，不要当失败。
  • 下载 tar 后立即 DELETE 释放 staging，避免占满共享卷。
  • 本服务无鉴权，VOS 内网可达；如需对外暴露请自行在网关加鉴权中间件。
